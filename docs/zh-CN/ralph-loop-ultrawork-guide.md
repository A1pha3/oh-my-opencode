# Ralph Loop 与 Ultrawork 协同使用指南

本文档详细说明 Ralph Loop（自参考开发循环）与 Ultrawork（极致工作模式）如何协同工作，以及如何组合使用以达到最高开发效率。

---

## 一、核心概念解析

### 1.1 什么是 Ralph Loop

Ralph Loop 是 Oh My OpenCode 中的一个核心功能，它实现了一个自参考开发循环机制。当启动 Ralph Loop 后，系统会持续监控会话状态，在检测到会话空闲且未完成时自动注入继续提示，驱动代理持续工作直到任务完全完成。

Ralph Loop 的核心特性包括以下几个方面。首先是自动继续机制，系统监听 `session.idle` 事件，当代理输出完成承诺标记时自动停止，否则自动注入继续提示。其次是迭代追踪，系统会记录当前迭代次数，并在每次继续时递增计数，防止无限循环。状态持久化也是重要特性，所有循环状态会保存到 `.sisyphus/ralph-loop.local.md` 文件中，即使会话中断也能恢复。完成承诺检测是另一个关键机制，系统会持续检测 `<promise>完成标记</promise>` 模式，识别任务是否完成。

### 1.2 什么是 Ultrawork

Ultrawork 是 Oh My OpenCode 中的一个工作模式激活器，通过在提示词中包含 `ultrawork` 或 `ulw` 关键词来触发。Ultrawork 模式会强制代理采用一套严格的工作规范，确保每个任务都经过充分的规划、探索和验证。

Ultrawork 模式的核心规范包括以下几个方面。强制规划原则要求所有非平凡任务必须调用计划代理，生成并行任务图和结构化待办列表。强制委托原则禁止代理直接执行任务，所有工作必须通过 `delegate_task` 委托给专业代理。强制验证原则要求在声明任务完成前必须提供可验证的证据。极致精确原则要求代理在行动前必须达到百分之百的确定性，不得做出假设或跳过关键步骤。

### 1.3 两者的关系分析

经过对代码库的深入分析，Ralph Loop 与 Ultrawork 之间**完全不存在冲突**，相反它们是**天然互补**的两个功能。Ralph Loop 提供了「持续工作的能力」，而 Ultrawork 提供了「高质量工作的规范」。两者结合可以实现「高质量的持续工作」这一理想状态。

从技术实现角度来看，两者的集成方式非常优雅。当 Ultrawork 与 Ralph Loop 一起使用时，`ultrawork` 标志会被存储在 Ralph Loop 的状态中。系统在每次继续循环时，如果检测到 `ultrawork=true`，会自动将 `ultrawork` 前缀添加到继续提示中。这意味着 Ultrawork 模式的严格规范会在每一次迭代中持续生效，确保整个长时间运行的任务都遵循高质量标准。

## 二、技术实现原理

### 2.1 Ralph Loop 的状态管理

Ralph Loop 的状态通过 `RalphLoopState` 接口进行管理，该接口定义了循环运行所需的全部状态信息。`active` 字段表示循环是否处于激活状态，`iteration` 字段记录当前迭代次数，`max_iterations` 字段设置最大迭代次数限制，`completion_promise` 字段定义完成承诺的文本内容，`ultrawork` 字段是关键的集成点，用于标记当前循环是否以 Ultrawork 模式运行。

当用户启动 Ralph Loop 时，系统会创建一个状态对象并写入到 `.sisyphus/ralph-loop.local.md` 文件中。每次循环继续时，系统会递增迭代计数并更新状态文件。如果会话中断，重新启动后系统会读取状态文件并从上次中断的地方继续执行。

### 2.2 Ultrawork 注入机制

Ultrawork 的注入发生在 Ralph Loop 的继续提示生成阶段。在 `src/hooks/ralph-loop/index.ts` 文件中，系统定义了 `CONTINUATION_PROMPT` 模板用于生成每次继续时的提示内容。当 `ultrawork=true` 时，系统会将 `ultrawork` 前缀添加到继续提示中，具体代码实现为：`const finalPrompt = newState.ultrawork ? \`ultrawork ${continuationPrompt}\` : continuationPrompt`。

这种设计确保了 Ultrawork 模式会在整个循环的每次迭代中持续生效。每次代理收到继续提示时，都会首先看到 Ultrawork 模式指令，然后才是个性化的继续内容。这保证了即使在长时间运行的任务中，Ultrawork 的严格规范也不会被遗忘或绕过。

### 2.3 关键词检测与模式路由

Ultrawork 的触发依赖于关键词检测钩子，该钩子位于 `src/hooks/keyword-detector/index.ts` 文件中。当用户输入中包含 `ultrawork` 或 `ulw` 时，系统会调用 `detectKeywordsWithType` 函数识别 Ultrawork 关键词，并根据当前代理类型路由到相应的 Ultrawork 消息模板。

对于不同类型的代理，系统会发送不同的 Ultrawork 消息。计划代理（如 Prometheus）会收到 `ULTRAWORK_PLANNER_SECTION` 消息，该消息强调规划者不应实现代码，而是专注于创建工作计划。GPT 5.2 模型会收到专门优化的消息。其他模型（包括 Claude 系列）会收到默认的 Ultrawork 消息，该消息包含完整的工作规范。

## 三、协同使用方法

### 3.1 基础启动方式

启动 Ultrawork 模式的 Ralph Loop 有两种等效方法。第一种方法是在任务描述中包含 Ultrawork 关键词，例如：`/ralph-loop "ulw 重构整个项目的错误处理模块"` 或 `/ralph-loop "ultrawork 完整实现用户认证功能"`。第二种方法是通过参数指定，例如：`/ralph-loop "重构整个项目" --ultrawork=true`。这两种方法效果完全相同，用户可以根据个人习惯选择。

当 Ultrawork 模式被激活时，Ralph Loop 会显示「Ultrawork Mode Activated」的提示消息，告知用户当前处于 Ultrawork 模式。在随后的每次迭代中，代理都会收到 Ultrawork 模式的指令，确保工作规范的一致性。

### 3.2 高级参数配置

对于复杂的长时间运行任务，用户可以结合使用多个参数来优化 Ralph Loop 的行为。以下是几个实用的配置示例。

第一个示例是最长运行配置，适用于需要数小时甚至数天才能完成的复杂任务：`/ralph-loop "ulw 完整重构微服务架构" --max-iterations=500 --completion-promise="MICROSERVICE_COMPLETE"`。这个配置将最大迭代次数设置为 500 次，并定义了自定义的完成承诺标记。

第二个示例是快速迭代配置，适用于需要频繁验证的小步迭代任务：`/ralph-loop "ulw 添加登录功能" --max-iterations=30`。这个配置使用较小的迭代次数限制，鼓励代理更频繁地验证和报告进度。

第三个示例是长时间运行配置，适用于跨天或跨周的大型项目：`/ralph-loop "ultrawork 完整实现电商平台" --max-iterations=1000 --completion-promise="E2E_COMPLETE"`。这个配置为大型项目提供了充足的迭代空间。

### 3.3 工作流程整合

Ultrawork 模式的 Ralph Loop 会自动遵循一个标准的工作流程，这个流程确保了每个任务都经过充分的规划、探索和验证。

在任务启动阶段，Ralph Loop 会记录任务描述和 Ultrawork 标志，然后进入循环监听状态。在上下文收集阶段，Ultrawork 规范要求代理在开始任何实现之前，必须首先通过 `explore` 和 `librarian` 代理收集足够的上下文信息。在规划阶段，对于非平凡任务，Ultrawork 要求代理调用计划代理生成并行任务图和结构化待办列表。在执行阶段，代理通过 `delegate_task` 将工作委托给专业代理，而不是直接执行所有任务。在验证阶段，代理必须在声明完成前提供可验证的证据，如测试通过、构建成功等。在迭代继续阶段，如果未检测到完成承诺，Ralph Loop 会自动注入继续提示，驱动代理继续工作。

## 四、最佳实践指南

### 4.1 任务描述的撰写规范

使用 Ultrawork 模式的 Ralph Loop 时，任务描述的质量直接影响最终结果。以下是撰写高质量任务描述的规范。

首先，任务描述应该**具体而非模糊**。避免使用「改进代码质量」这样的模糊描述，而应该使用「将所有 REST API 响应时间优化到 200ms 以下」这样具体的描述。具体的目标更容易被验证，也更容易让代理理解用户的真实需求。

其次，任务描述应该**包含验收标准**。在描述中明确说明什么样的结果被认为是「完成」，例如：「完成标准是所有测试用例通过，构建成功，且 API 文档更新完毕」。这有助于 Ralph Loop 在适当时机正确检测任务完成。

第三，任务描述应该**控制范围**。Ultrawork 模式擅长处理复杂任务，但过大的范围可能导致迭代次数不足或上下文过于庞大。建议将超大型项目拆分为多个阶段，每个阶段使用独立的 Ralph Loop 会话。

### 4.2 迭代次数的合理设置

迭代次数的设置需要根据任务复杂度和可用时间进行权衡。以下是一些经验性的指导原则。

对于简单任务，如单文件修复或小型功能添加，建议设置 30 到 50 次迭代。这类任务通常可以在几次迭代内完成，较少的迭代次数可以更快地获得反馈。

对于中等任务，如多文件重构或中等复杂度功能实现，建议设置 100 到 200 次迭代。这为代理提供了足够的空间进行探索、实现和验证。

对于复杂任务，如跨模块重构或系统级变更，建议设置 300 到 500 次迭代。这类任务可能需要多次探索和迭代才能完全完成。

对于超大型任务，如完整系统迁移或新平台搭建，建议设置 500 次以上的迭代，甚至可以使用 `ulw-loop` 命令实现无限制迭代。

### 4.3 完成承诺的选择策略

完成承诺标记是 Ralph Loop 检测任务完成的关键机制。选择合适的完成承诺标记可以提高任务管理的清晰度。

使用默认承诺是最简单的选择，`DONE` 是 Ralph Loop 的默认完成承诺。当代理输出 `<promise>DONE</promise>` 时，系统会认为任务完成。这种方式适用于大多数场景，特别是当用户不关心区分不同任务的完成状态时。

使用自定义承诺可以提高可追溯性。例如，使用 `AUTH_COMPLETE` 表示认证模块完成，使用 `API_REFACTORED` 表示 API 重构完成。这种方式特别适用于同时运行多个 Ralph Loop 任务的情况，便于区分每个任务的完成状态。

使用阶段承诺适用于大型项目。例如，`PHASE_1_COMPLETE` 表示第一阶段完成，允许用户在特定里程碑后进行干预或调整后续计划。

### 4.4 并行任务的高效组织

Ultrawork 模式强调使用并行任务图来最大化效率。以下是在 Ralph Loop 中组织并行任务的最佳实践。

首先，在开始实现之前，应该先规划任务依赖关系。识别哪些任务可以并行执行，哪些任务有依赖关系需要顺序执行。独立的任务应该尽可能并行启动，以充分利用系统资源。

其次，使用 `delegate_task` 的 `run_in_background=true` 参数启动并行任务。例如：`delegate_task(category="quick", load_skills=["git-master"], run_in_background=true)` 可以同时启动多个后台任务。

第三，使用 `background_output` 收集并行任务的结果，然后再继续依赖这些结果的后续任务。这种方式既保证了并行效率，又确保了数据依赖的正确性。

### 4.5 长时间运行任务的管理

对于需要数小时甚至数天才能完成的复杂任务，以下策略可以帮助提高成功率。

第一，确保任务描述足够清晰。由于 Ralph Loop 可能运行很长时间，期间可能经历多次上下文截断，清晰的任务描述可以帮助代理保持正确的方向。

第二，设置合理的检查点。在任务描述中明确中间里程碑，例如：「第一阶段完成后报告进度」。这允许用户在长时间运行过程中进行干预和验证。

第三，使用会话恢复功能。Ralph Loop 会将状态保存到文件中，即使会话中断也可以通过 `/start-work` 命令从上次中断的地方继续。

第四，考虑使用 ulw-loop 命令。对于真正需要无限制运行的超大型任务，可以使用 `ulw-loop` 命令，它本质上是设置了超长迭代次数的 Ralph Loop。

## 五、常见使用场景

### 5.1 大规模代码重构

场景描述：需要重构整个项目的错误处理模块，将分散的错误处理逻辑统一到新的错误处理框架中。

推荐命令：`/ralph-loop "ulw 统一项目中的所有错误处理逻辑，使用新的 ErrorHandler 类" --max-iterations=200 --completion-promise="ERROR_HANDLING_REFACTORED"`

工作流程如下。首先，代理会使用 `explore` 代理搜索项目中所有包含错误处理的文件。然后，使用 `librarian` 代理研究现代错误处理的最佳实践。接着，代理会生成重构计划，包括需要修改的文件清单、修改顺序和验证步骤。在执行阶段，代理会分批修改文件，并使用 `ultrabrain` 类别处理复杂的逻辑变更。在验证阶段，代理会运行测试套件确保所有功能正常工作。最后，当代理输出 `<promise>ERROR_HANDLING_REFACTORED</promise>` 时，Ralph Loop 自动停止。

### 5.2 复杂功能完整实现

场景描述：需要实现完整的用户认证功能，包括登录、注册、密码重置、会话管理等。

推荐命令：`/ralph-loop "ultrawork 实现完整的 JWT 用户认证系统，包括登录、注册、密码重置和会话管理" --max-迭代次数=300 --completion-promise="AUTH_SYSTEM_COMPLETE"`

工作流程如下。首先，代理会研究现有的认证模式和安全最佳实践。然后，生成详细的实现计划，包括数据库模型、API 端点、前端集成等。在实现阶段，代理会并行实现不同的组件，使用 `visual-engineering` 类别处理前端界面，使用 `ultrabrain` 类别处理安全相关的后端逻辑。在集成阶段，代理会将各个组件组合成完整的系统。在测试阶段，代理会进行端到端测试确保所有功能正常工作。

### 5.3 自动化代码清理

场景描述：清理项目中的技术债务，包括移除未使用的导入、修复 TypeScript 错误、标准化代码风格等。

推荐命令：`/ralph-loop "ulw 清理项目中的所有技术债务，移除未使用的导入，修复所有 TypeScript 编译错误，标准化代码风格" --max-iterations=100 --completion-promise="TECHNICAL_DEBT_CLEARED"`

工作流程如下。首先，代理会使用 `lsp_diagnostics` 工具获取所有错误的清单。然后，优先处理阻断性错误，再处理警告和提示。在清理阶段，代理会使用 `quick` 类别处理简单的清理任务。在验证阶段，代理会在每次修改后运行类型检查确保没有引入新问题。

### 5.4 跨平台迁移项目

场景描述：将项目从一种技术栈迁移到另一种技术栈，如从 JavaScript 迁移到 TypeScript，或从 REST 迁移到 GraphQL。

推荐命令：`/ralph-loop "ultrawork 将整个后端服务从 Express REST API 迁移到 Apollo Server GraphQL，保持所有功能不变" --max-iterations=500 --completion-promise="MIGRATION_COMPLETE"`

工作流程如下。首先，代理会分析现有的 REST API 结构和业务逻辑。然后，研究目标技术栈的最佳实践和迁移策略。在迁移阶段，代理会分模块进行迁移，每个模块包括类型定义、解析器、服务层和测试。在验证阶段，代理会确保迁移后的功能与原始实现完全一致。

## 六、与其它功能的协同

### 6.1 与 Todo 继续强制器的协同

Todo 继续强制器是 Oh My OpenCode 的另一个核心功能，它强制代理在声明任务完成前必须完成所有 TODO 项目。Ultrawork 模式的 Ralph Loop 与 Todo 继续强制器天然协同工作。

当 Ultrawork 模式的 Ralph Loop 运行时，代理在每次迭代中都会收到双重约束。一方面，Ralph Loop 要求代理持续工作直到输出完成承诺。另一方面，Todo 继续强制器要求代理完成所有 TODO 项目才能输出完成承诺。这种双重约束确保了任务不仅被完成，而且是被完整地完成。

### 6.2 与后台代理系统的协同

后台代理系统允许 Ralph Loop 在单次迭代中启动多个并行任务。这对于 Ultrawork 模式特别重要，因为 Ultrawork 强调「并行第一」的执行原则。

在 Ultrawork 模式的 Ralph Loop 中，代理可以同时启动多个后台探索任务来收集上下文，并行实现多个独立的功能模块，并在每次迭代中最大化资源利用率。Ralph Loop 会持续运行直到所有后台任务完成且输出完成承诺。

### 6.3 与 Atlas 编排器的协同

Atlas 是 Oh My OpenCode 的主编排器，负责协调复杂任务的执行。当 Ultrawork 模式的 Ralph Loop 与 Atlas 协同工作时，Atlas 会收到 Ultrawork 模式的指令，这会影响它的工作方式。

在 Ultrawork 模式下，Atlas 会更加积极地使用 `delegate_task` 将工作委托给专业代理，而不是直接执行所有任务。Atlas 会更加注重在执行前进行充分的探索和规划。Atlas 会更加严格地要求验证每个步骤的完成情况。

### 6.4 与会话恢复功能的协同

会话恢复功能允许 Ralph Loop 在会话中断后从上次中断的地方继续。这对于 Ultrawork 模式的长时间运行任务特别重要。

当 Ultrawork 模式的 Ralph Loop 会话中断时，系统会保存当前的迭代次数、任务状态和 Ultrawork 标志。用户重新连接后，可以使用 `/start-work` 命令恢复会话，系统会自动从上次中断的地方继续执行 Ultrawork 模式的循环。

## 七、监控与调试

### 7.1 循环状态监控

Ralph Loop 在运行时会生成多种日志信息，帮助用户监控循环的状态。用户可以通过以下方式获取循环状态信息。

首先，循环状态会写入 `.sisyphus/ralph-loop.local.md` 文件，该文件包含当前的迭代次数、开始时间、任务描述和完成承诺。其次，系统日志会记录循环的每次继续，包括当前迭代次数和剩余迭代次数。第三，完成检测日志会记录任务完成的检测结果，包括检测方式和完成承诺内容。

### 7.2 进度追踪策略

在长时间运行的 Ultrawork 模式 Ralph Loop 任务中，追踪进度可能具有挑战性。以下是一些有效的进度追踪策略。

第一种策略是设置中间检查点。在任务描述中明确要求代理在特定阶段报告进度，例如：「每完成 10 个文件修改后报告进度」。这种方式允许用户在任务进行过程中了解当前状态。

第二种策略是使用 TODO 列表追踪。Ultrawork 模式要求代理生成结构化 TODO 列表，用户可以通过检查 TODO 列表的完成情况来了解进度。

第三种策略是使用 commit 记录。如果代理在实现过程中进行提交，用户可以通过 git log 查看已完成的更改。

### 7.3 常见问题与解决方案

问题一：循环似乎陷入了死循环。解决方案是检查代理是否输出了完成承诺，确认完成承诺标记是否正确。如果代理已经输出完成承诺但系统未检测到，可能是标记格式问题。建议使用默认的 `DONE` 承诺或检查自定义承诺的格式是否匹配。

问题二：Ultrawork 模式没有生效。解决方案是确认任务描述中包含 `ultrawork` 或 `ulw` 关键词，或者使用了 `--ultrawork=true` 参数。也可以检查系统日志确认 Ultrawork 模式是否被正确激活。

问题三：迭代次数不足导致任务未完成。解决方案是增加 `--max-iterations` 参数的值。对于非常长的任务，建议使用 `ulw-loop` 命令。

问题四：会话中断后无法恢复。解决方案是确认 `.sisyphus/ralph-loop.local.md` 文件存在且包含正确的状态信息。然后使用 `/start-work` 命令尝试恢复会话。

## 八、命令参考

### 8.1 Ralph Loop 命令

Ralph Loop 的基本命令格式为 `/ralph-loop "任务描述" [参数]`。

可用的参数包括：`--max-iterations=N` 用于设置最大迭代次数，默认值为 100；`--completion-promise=TEXT` 用于设置完成承诺标记，默认值为 DONE；`--ultrawork=true` 用于显式启用 Ultrawork 模式。

### 8.2 Ultrawork 相关命令

Ultrawork 可以通过多种方式激活。最简单的方式是在任务描述中包含 `ultrawork` 或 `ulw` 关键词，例如：`ulw 重构代码`。也可以使用 `--ultrawork=true` 参数显式激活。

### 8.3 取消命令

取消正在运行的 Ralph Loop 可以使用 `/cancel-ralph` 命令。执行此命令后，系统会清除循环状态并停止自动继续。

### 8.4 ulw-loop 命令

ulw-loop 是 Ralph Loop 的一种变体，专门为 Ultrawork 模式设计，本质上是无限制迭代的 Ralph Loop。命令格式为 `/ulw-loop "任务描述"`，默认使用 `DONE` 作为完成承诺。

## 九、总结与建议

Ralph Loop 与 Ultrawork 是 Oh My OpenCode 中两个相互补充的核心功能。Ralph Loop 提供了「持续工作的能力」，确保任务在被明确完成之前不会停止。Ultrawork 提供了「高质量工作的规范」，确保每个任务都经过充分的规划、探索和验证。两者的结合可以实现「高质量的持续工作」这一理想状态。

对于日常使用，建议遵循以下原则。首先，对于简单任务可以直接使用 Ultrawork 关键词，无需启动 Ralph Loop。其次，对于需要持续工作的复杂任务，优先使用 Ultrawork 模式的 Ralph Loop。第三，对于超大型项目，考虑使用 ulw-loop 或设置较高的迭代次数限制。第四，始终设置清晰的验收标准和完成承诺，便于系统正确检测任务完成。

通过合理组合使用 Ralph Loop 和 Ultrawork，用户可以实现真正意义上的「自动化开发」——只需描述想要什么，系统会自动完成所有工作，直到交付可用的结果。这正是 Oh My OpenCode 核心哲学的体现：「人在环路是失败的信号」。
